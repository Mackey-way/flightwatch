# Развёртывание агентом

Этот файл — для LLM-агента, которому дали ссылку на репозиторий и доступ по
ssh к серверу. Человеку достаточно `README.md`.

Проверено на чистом Debian 12 (bookworm) в двух вариантах: с systemd и без
него. Всё, что ниже, — реально прогнанная последовательность, а не план.

## 0. Чего делать НЕЛЬЗЯ

* **Не выдумывай секреты.** Токен Telegram, chat_id и номер телефона знает
  только человек. Если их не дали — ставь без них (`FW_TG_TOKEN=""`), система
  поднимется и будет молча следить; каналы допишутся потом одной правкой
  конфига.
* **Не клади секреты в `config.json`.** Там только пути к файлам. Файлы
  создаёт установщик, права `640 root:flightwatch`.
* **Не открывай брокер наружу.** `listener 1883 127.0.0.1` — это не
  перестраховка: с `allow_anonymous false` и без ACL любой, кто дотянется до
  порта, сможет слать команды на отправку СМС.
* **Не перезапускай демон после правки конфига.** Он перечитывает файл сам
  по `mtime`, цикл 90 секунд. Перезапуск не ускорит и потеряет состояние.
* **Не считай `systemctl is-active` доказательством работы.** paho отдаёт
  отказ аутентификации асинхронно: при неверном пароле к брокеру юнит будет
  `active` с мёртвым каналом. Доказательство — строка `MQTT: подключён` в
  журнале.

## 1. Что спросить у человека до начала

| нужно | зачем | если не дали |
|---|---|---|
| `FW_TG_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) | ставь без Telegram |
| `FW_TG_CHAT` | числовой chat_id получателя | `0` |
| `FW_SMS_TO` | номер `+7…` для СМС | ставь с заглушкой (см. ниже) |
| `FW_SMS_TOPIC` | топик его настоящего SMS-шлюза | `smsgw/mock/sms/send` |

**Про СМС.** Настоящий шлюз — это чей-то модем с симкой, и его почти
наверняка нет. Ставь с `--with-mock-sms`: заглушка выполняет тот же контракт,
канал СМС при этом живой и проверяемый целиком, но никуда ничего не уходит.
Не пытайся настроить настоящую отправку, если человек про неё не просил.

chat_id узнаётся так: человек пишет боту любое сообщение, затем

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" | grep -o '"id":[0-9-]*' | head -1
```

Важно: `getUpdates` держит **один** процесс. Если у бота уже висит вебхук или
другой поллер, ответ будет пустым — это не ошибка токена.

## 2. Установка

```bash
git clone <URL репозитория> /tmp/flightwatch-oss
cd /tmp/flightwatch-oss
sudo FW_TG_TOKEN="…" FW_TG_CHAT=… ./install.sh --yes --with-mock-sms --with-fwapi
```

Скрипт идемпотентный: повторный запуск не перетирает уже созданные секреты и
конфиг. Флаги: `--with-mock-sms` (заглушка шлюза), `--with-fwapi` (контракт
для агента), `--skip-db`, `--skip-broker`, `--skip-packages`.

Он проходит 9 шагов и **останавливается на первом же несошедшемся**. Не
продолжай вручную мимо остановки — сообщение всегда называет причину.

## 3. Проверка — по одной команде на утверждение

Каждая строка проверяет ровно одно. Если хоть одна не сошлась, дальше не иди.

```bash
# служба жива
systemctl is-active flightwatch                 # ожидается: active

# канал до брокера ЖИВОЙ, а не просто "процесс запущен"
journalctl -u flightwatch -n 50 --no-pager | grep "MQTT: подключён"

# база на месте: 15 таблиц + 7 представлений
sudo mysql -N -B -e \
  "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='flightwatch';"
# ожидается: 22

# источники реально опрашиваются (после того как добавлен хотя бы один рейс)
sudo mysql -N -B flightwatch -e \
  "SELECT source, ok, rows_returned FROM source_polls ORDER BY id DESC LIMIT 3;"
# ожидается: ok=1 и ненулевое число строк
```

Живой прогон целиком — добавить рейс и дождаться цикла:

```bash
sudo -u flightwatch /opt/flightwatch/venv/bin/python \
     /opt/flightwatch/flightwatch.py --add 3F151 $(date -d '+2 days' +%F) EVN
sleep 100
journalctl -u flightwatch -n 10 --no-pager
# ожидается: "конфиг перечитан, рейсов: 1" и затем строка про сам рейс
```

`EVN` тут не случаен: у Звартноца открытый JSON без ключа, он отвечает
всегда, и это самый дешёвый способ доказать, что сетевой путь работает. Ответ
«не найден (1 проверок подряд, порог 3)» — **нормальный**: рейс за двое суток
ещё не на табло, а порог в 3 проверки как раз для этого и стоит.

Канал СМС, если ставили с `--with-mock-sms` — проверяется целиком, без симки:

```bash
mosquitto_pub -h 127.0.0.1 -u flightwatch \
  -P "$(sudo cat /opt/flightwatch/.mqtt_pass)" -t smsgw/mock/sms/send \
  -m '{"to":"+70000000000","text":"проверка","req_id":"fw-test-1"}'
sleep 2 && sudo cat /opt/flightwatch/run/sms-mock.jsonl
# ожидается строка JSON с текстом "проверка"
journalctl -u flightwatch --since "-1 min" --no-pager | grep "мост подтвердил"
```

Если ставили с `--with-fwapi`:

```bash
sleep 3                           # службе нужен момент, чтобы занять порт
fwctl status                      # читает, ничего не меняет
fwctl sources --hours 1           # ходит в базу под fwread
fwctl sql "DELETE FROM flights"   # ожидается отказ: "разрешены только SELECT и WITH"
```

## 4. Что ломается чаще всего

| симптом | причина | что делать |
|---|---|---|
| `ОСТАНОВ: MariaDB не отвечает` | СУБД не запущена (частое в контейнере) | `systemctl start mariadb`, без systemd — `mariadbd-safe --user=mysql &` |
| `БРОКЕР НЕ ОТВЕЧАЕТ … Connection refused` | mosquitto не стартовал | `systemctl status mosquitto`; чаще всего — дубль директивы в `conf.d` |
| `Error: Duplicate persistence_location` | в стоковом `mosquitto.conf` Debian это уже задано | убрать `persistence*` из своего файла в `conf.d` |
| `БРОКЕР НЕ ПУСТИЛ: Not authorized` | пароль в `/etc/mosquitto/passwd` и в `.mqtt_pass` разошлись | `mosquitto_passwd -b /etc/mosquitto/passwd flightwatch "$(cat /opt/flightwatch/.mqtt_pass)"` и перезапустить брокер |
| `PermissionError: /opt/flightwatch/state.tmp` | старая версия писала состояние рядом с кодом | обновить `flightwatch.py`: состояние живёт в `run/` |
| юнит `active`, но сообщений нет | демон не подключился к брокеру | искать в журнале `MQTT НЕ ПОДКЛЮЧЁН` |
| `токен Telegram не задан` | Telegram не настроен | это не ошибка, если токена нет намеренно |
| `СМС НЕ ПОДТВЕРЖДАЮТСЯ` | шлюза нет на месте | `systemctl status mock-sms-gw`; заглушку надо поднимать до демона |
| `mysql: Access denied` при заливке схемы | заливаете не под root@localhost | `sudo mysql flightwatch < docs/schema.sql`; `DEFINER` из дампа уже вырезаны |

## 5. Разнесённая установка (облако + дом)

Ставится **после** того, как одиночная установка проверена. Порядок такой и
менять его не стоит — каждый следующий шаг проверяется предыдущим:

1. фаервол на облаке (открыт только ssh и `51820/udp`);
2. WireGuard, `AllowedIPs` по одному `/32` в каждую сторону
   (`extras/split-deployment/wg0-*.conf`), проверка — `ping` до адреса в туннеле;
3. перенос демона и базы, проверка — совпадение числа строк по каждой таблице;
4. мост MQTT (`extras/split-deployment/mosquitto-bridge.conf`) и ACL на домашнем брокере
   (`extras/split-deployment/mosquitto-acl`), проверка — команда на СМС, отправленная при
   выключенном туннеле, должна дойти после включения;
5. параллельный прогон: облачный экземпляр с **другими** `mqtt_prefix` и
   `mqtt_client_id` и `notify: false`, сутки рядом с домашним;
6. переключение: поменять роли местами.

Одинаковый `mqtt_client_id` у двух экземпляров — это дуэль сессий, брокер
будет бесконечно выкидывать то одного, то другого. Разные префиксы нужны,
чтобы теневой экземпляр не перетирал сенсоры боевого.

## 6. Если ставите ещё и агента

`agent/SKILL.md` написан под OpenClaw, но это обычный markdown — переносится
в любой рантайм. Главное не в скиле, а в границе: у пользователя агента
**не должно быть** доступа к `/opt/flightwatch`. Ставится это ядром, а не
просьбой в промпте:

```ini
# в юните агента
InaccessiblePaths=/opt/flightwatch /root /etc/wireguard /etc/mosquitto
NoNewPrivileges=true
```

Агент ходит только через `fwctl` / `fwctl-write`, а доступ к токену ему даёт
членство в группе `fwapi` — и ничего кроме. `fwctl-config` в allowlist
добавлять не надо: она меняет поведение всей системы, и подтверждение там по
делу.

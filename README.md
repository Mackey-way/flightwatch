# flightwatch

Демон слежения за конкретными рейсами. Опрашивает табло аэропортов и FR24,
замечает изменения раньше, чем о них объявят, и пишет человеку в Telegram и
СМС. СМС уходят через собственный модем — то есть доходят и тогда, когда
интернета у адресата нет.

Задача не «показать статус рейса», а **разбудить решением**: пора выезжать,
стыковка под угрозой, борт под ваш рейс ещё не вылетел, аэропорт сыплется.
Всё, что не требует действия, система молчит.

## Что она умеет

* **Несколько источников на аэропорт.** Публичный шлюз TAV, открытый JSON
  Звартноца, табло Черногории, XML Белграда, FR24 как общий запасной. У
  каждого источника свой горизонт и свои поля; при осечке молча откат на
  следующий, с экспоненциальным отстоем.
* **Ротация борта.** Самый ранний сигнал: борт, который ещё не вылетел в
  вашу сторону, делает вылет по расписанию невозможным за много часов до
  того, как табло признает задержку.
* **Стыковка.** Считается не «рейс опоздал на N», а «до закрытия выхода на
  следующий рейс осталось M минут» — решение принимается по второму.
* **Сбой аэропорта.** Оценивается по всей доске в операционном окне, а не по
  вашим пяти рейсам. Пороги входа и выхода разные — иначе на границе
  начинается дребезг и сообщения каждые полчаса.
* **Прогноз опоздания** с записью горизонта в базу, чтобы веса можно было
  калибровать по факту, а не на глаз.
* **Плановые сводки.** Молчание недоказательно: в заданное время приходит
  сводка, даже когда всё спокойно, — иначе человек не знает, жива ли система.
* **Сенсоры Home Assistant** через MQTT discovery (по желанию).
* **Контракт для LLM-агента** — узкий набор операций, см. ниже.

## Топология

Базовая установка — **одна машина**: демон, MariaDB, mosquitto. Ни модема, ни
второго сервера, ни туннеля не нужно. Telegram работает сразу; канал СМС при
этом тоже работает — на заглушке, которая принимает команды и подтверждает
их, но никуда не звонит.

```
  ┌─────────────────────────────────────────┐
  │  flightwatch ──► Telegram               │
  │      │                                  │
  │      └──MQTT──► SMS-шлюз ──► (заглушка) │
  │  MariaDB   mosquitto                    │
  └─────────────────────────────────────────┘
```

Заглушка (`tools/mock_sms_gw.py`) — не декорация: она реализует тот же
контракт, что настоящий шлюз, и умеет изображать отказ, молчание и лимит
частоты. То есть все ветки канала СМС — очередь, подтверждение, срок
годности, тревога «канал лёг» — проверяются без единой симки. Контракт
описан в [docs/sms-gateway-contract.md](docs/sms-gateway-contract.md): чтобы
слать настоящие СМС, достаточно поставить на место заглушки что угодно, что
его выполняет.

Всё, что специфично для конкретной установки, вынесено в `extras/` и в
базовой установке не участвует:

* `extras/openstick/` — мост под конкретный USB-модем: реальная реализация
  того же контракта, годится как образец;
* `extras/split-deployment/` — разнесённый вариант «демон в облаке, СМС
  через дом»: WireGuard, мост mosquitto и ACL брокера.

## Быстрая установка

Проверено на чистом Debian 12. Одна команда ставит всё: пакеты, базу со
схемой, брокер с учёткой, окружение python, конфиг, службы — и на каждом шаге
проверяет результат, останавливаясь на первом же несошедшемся.

```bash
git clone <URL> flightwatch && cd flightwatch
sudo FW_TG_TOKEN='токен от @BotFather' FW_TG_CHAT=123456789 \
     ./install.sh --yes --with-mock-sms --with-fwapi
```

Без секретов тоже поднимется — молча следить и писать в базу он будет и так,
Telegram дописывается потом одной правкой конфига:

```bash
sudo ./install.sh --yes --with-mock-sms
```

`--with-mock-sms` ставит заглушку шлюза. Настоящие СМС для этого не нужны, а
канал при этом живой: команды уходят, подтверждения приходят, «отправленное»
копится в `/opt/flightwatch/run/sms-mock.jsonl`. Когда появится настоящий
шлюз — поменяется одна строка `sms_topic` в конфиге.

Скрипт идемпотентный: повторный запуск не перетирает ни секреты, ни конфиг.
Флаги: `--with-fwapi`, `--skip-db`, `--skip-broker`, `--skip-packages`, `--yes`.

Дальше — проверка, что оно действительно живое, а не просто «запустилось»:

```bash
journalctl -u flightwatch -n 50 --no-pager | grep "MQTT: подключён"
```

Эта строка и есть доказательство. `systemctl is-active` его не даёт: paho
отдаёт отказ аутентификации асинхронно, и при неверном пароле к брокеру юнит
будет `active` с мёртвым каналом.

Разворачиваете агентом? Тогда ему нужен [AGENTS.md](AGENTS.md) — там
последовательность с проверкой после каждого шага и таблица типовых поломок.

## Ручная установка

Если хочется понимать, что происходит, или ставить не на Debian.

### 0. Что нужно на сервере

Debian 12 / Ubuntu 22.04 и новее, 1 ГБ памяти хватает.

```bash
sudo apt update && sudo apt install -y python3 python3-venv python3-pip tzdata \
     mariadb-server mariadb-client mosquitto mosquitto-clients
```

`tzdata` не роскошь: всё время в системе считается через `zoneinfo` на момент
события, а не по словарю смещений — без базы часовых поясов расчёты поедут.

### 1. База

```bash
sudo mysql -e "CREATE DATABASE flightwatch CHARACTER SET utf8mb4;"
sudo mysql -e "CREATE USER 'flightwatch'@'127.0.0.1' IDENTIFIED BY 'ПАРОЛЬ';"
sudo mysql -e "GRANT ALL ON flightwatch.* TO 'flightwatch'@'127.0.0.1';"
sudo mysql flightwatch < docs/schema.sql
```

Справочные таблицы (`airline_rules`, `airport_rules`, `travel_profiles`,
`connect_defaults`) приезжают пустыми — демон работает и без них, они только
уточняют оценки.

Если планируете `fwapi`, заведите ещё и **читающего** пользователя: `fwctl
sql` ходит именно им, поэтому «только SELECT» держится не регуляркой, а
правами базы.

```bash
sudo mysql -e "CREATE USER 'fwread'@'127.0.0.1' IDENTIFIED BY 'ПАРОЛЬ2';"
sudo mysql -e "GRANT SELECT ON flightwatch.* TO 'fwread'@'127.0.0.1';"
```

### 2. Каталог и права

Демон не должен уметь переписывать собственный код — отсюда разделение
владельцев и отдельный подкаталог `run/` под всё изменяемое.

```bash
sudo useradd -r -s /usr/sbin/nologin flightwatch
sudo mkdir -p /opt/flightwatch/run
sudo cp src/flightwatch.py /opt/flightwatch/
sudo chown -R root:root /opt/flightwatch
sudo chown flightwatch:flightwatch /opt/flightwatch/run
```

Конфиг лежит в `run/`, а в каталоге кода на него симлинк. Так и каталог кода
остаётся закрытым на запись, и атомарная подмена файла работает: `os.replace`
требует права на **каталог**, а не на файл.

```bash
# в примере flights пустой — рейсы добавляются потом, см. шаг 5b
sudo cp config.example.json /opt/flightwatch/run/config.json
sudo ln -s run/config.json /opt/flightwatch/config.json
sudo chown flightwatch:flightwatch /opt/flightwatch/run/config.json
sudo chmod 640 /opt/flightwatch/run/config.json
```

### 3. Секреты — файлами, не в конфиге

```bash
printf '%s' 'ПАРОЛЬ'        | sudo tee /opt/flightwatch/.mysql_pass >/dev/null
printf '%s' 'ПАРОЛЬ_MQTT'   | sudo tee /opt/flightwatch/.mqtt_pass  >/dev/null
printf '%s' 'ТОКЕН_БОТА'    | sudo tee /opt/flightwatch/.tg_token   >/dev/null
sudo chmod 640 /opt/flightwatch/.*_pass /opt/flightwatch/.tg_token
sudo chown root:flightwatch /opt/flightwatch/.*_pass /opt/flightwatch/.tg_token
```

В конфиге хранятся только **пути** к этим файлам. В репозитории их нет и быть
не должно — см. `.gitignore`.

### 3b. Брокер MQTT

```bash
# без -c mosquitto_passwd не создаёт файл, а падает на отсутствующем
sudo touch /etc/mosquitto/passwd
sudo mosquitto_passwd -b /etc/mosquitto/passwd flightwatch 'ПАРОЛЬ_MQTT'
sudo chown root:mosquitto /etc/mosquitto/passwd && sudo chmod 640 /etc/mosquitto/passwd
sudo tee /etc/mosquitto/conf.d/flightwatch.conf >/dev/null <<'EOF'
listener 1883 127.0.0.1
allow_anonymous false
password_file /etc/mosquitto/passwd
EOF
sudo systemctl restart mosquitto && systemctl is-active mosquitto
```

`persistence` и `persistence_location` сюда добавлять **не надо**: в стоковом
`/etc/mosquitto/mosquitto.conf` Debian они уже есть, а повторное значение
mosquitto считает ошибкой конфигурации и отказывается стартовать целиком.

Права на `passwd` обязательны: файл читает процесс mosquitto, и при `600
root:root` брокер молча не пустит никого.

### 3c. Бот Telegram

Создать бота у [@BotFather](https://t.me/BotFather), затем написать ему любое
сообщение и забрать chat_id:

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" \
  | grep -o '"id":[0-9-]*' | head -1
```

Пустой ответ при рабочем токене означает, что `getUpdates` уже держит другой
процесс или у бота стоит вебхук — поллер может быть только один.

### 4. Окружение и запуск

```bash
sudo python3 -m venv /opt/flightwatch/venv
sudo /opt/flightwatch/venv/bin/pip install -r requirements.txt
sudo cp systemd/flightwatch.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now flightwatch
```

Проверка, что он действительно поднялся, а не просто «active»:

```bash
sleep 5 && journalctl -u flightwatch -n 40 --no-pager | grep -E "MQTT|рейс"
```

В логе должна быть строка `MQTT: подключён`. Это не украшение: paho отдаёт
ошибку аутентификации асинхронно, `connect()` при неверном пароле не падает —
юнит будет `active` с мёртвым брокером, пока не посмотришь в лог.

### 5. Конфиг

Скопируйте `config.example.json` и правьте. Ключи, которые нужны сразу:

| ключ | что это |
|---|---|
| `flights` | список отслеживаемых рейсов (см. ниже) |
| `channels` | `["telegram", "sms"]` — порядок и есть приоритет |
| `telegram_chat_id`, `telegram_token_file` | куда и чем писать |
| `sms_to`, `sms_topic`, `ack_topic` | номер и топики моста СМС |
| `mqtt_*` | брокер; `mqtt_client_id` уникален **на каждый экземпляр** |
| `discovery_prefix` | префикс MQTT discovery для Home Assistant |
| `notify` | глобальный выключатель отправки |
| `briefings` | плановые сводки: время местное для указанного аэропорта |

Рейс:

```json
{
  "flight": "XX1234", "date": "2026-01-01", "airport": "AAA",
  "direction": "departure", "to": "BBB",
  "title": "Город А - Город Б",
  "owner": "self",
  "mct_min": 60, "gate_close_min": 20,
  "extra_sms_to": []
}
```

`owner: "other"` — чужой рейс, за которым следят ради встречи. Влияет на
формулировки: будить владельца телефона «пора выезжать» по чужому рейсу
нельзя.

Демон перечитывает конфиг сам по `mtime`, цикл — `poll_seconds` (90 с по
умолчанию). Перезапуск после правки не нужен.

### 5b. Первый рейс и проверка живьём

Рейсы правятся и с командной строки, и прямо в `config.json` — путь внутрь
один и тот же:

```bash
sudo -u flightwatch /opt/flightwatch/venv/bin/python \
     /opt/flightwatch/flightwatch.py --add 3F151 2026-09-09 EVN
sudo -u flightwatch /opt/flightwatch/venv/bin/python \
     /opt/flightwatch/flightwatch.py --list
```

`EVN` для проверки удобен тем, что у Звартноца открытый JSON без ключа —
самый дешёвый способ доказать, что сетевой путь работает. Через полторы
минуты в журнале должно появиться `конфиг перечитан, рейсов: 1`, а в базе —
удачный опрос:

```bash
sudo mysql -N -B flightwatch -e \
  "SELECT source, ok, rows_returned FROM source_polls ORDER BY id DESC LIMIT 3;"
```

Ответ демона «не найден (1 проверок подряд, порог 3)» — нормальный: рейса за
двое суток на табло ещё нет, порог в три проверки ровно для этого.

### 5c. Сенсоры в Home Assistant

Если в `discovery_prefix` указан ваш префикс discovery (по умолчанию
`homeassistant`) и HA слушает тот же брокер, сенсоры появятся сами — по
одному устройству на рейс. Отдельной настройки в HA не требуется.

Не нужны — уберите `discovery_prefix` из конфига, публикация прекратится.

### 6. Канал СМС

По умолчанию демон публикует команды в `smsgw/mock/sms/send` и слушает
подтверждения на `smsgw/+/sms/sent`. На другом конце стоит заглушка:

```bash
sudo install -d /opt/flightwatch/tools
sudo install -m 755 tools/mock_sms_gw.py /opt/flightwatch/tools/
sudo cp systemd/mock-sms-gw.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now mock-sms-gw
sleep 3 && systemctl is-active mock-sms-gw
```

Пауза не для красоты: пока заглушка не подключилась к брокеру и не оформила
подписку, команда, отправленная в этот момент, не попадёт никуда — сессии,
в которую её можно было бы положить, ещё не существует.

Проверить канал целиком, не дожидаясь события по рейсу:

```bash
mosquitto_pub -h 127.0.0.1 -u flightwatch \
  -P "$(sudo cat /opt/flightwatch/.mqtt_pass)" -t smsgw/mock/sms/send \
  -m '{"to":"+70000000000","text":"проверка","req_id":"fw-test-1"}'
sleep 2 && sudo cat /opt/flightwatch/run/sms-mock.jsonl
journalctl -u flightwatch --since "-1 min" --no-pager | grep "мост подтвердил"
```

Заглушка умеет изображать поломки — это нужно, чтобы убедиться, что тревога
приходит, а не что «в норме всё хорошо»:

| ключ | что изображает | что видно в `journalctl -u flightwatch` |
|---|---|---|
| `--fail-rate 1.0` | шлюз отвечает отказом | `ERROR КАНАЛ СМС НЕ РАБОТАЕТ … MockDeliveryFailure` |
| `--silent` | шлюз молчит | то же, но `мост не подтвердил N сообщений` — и в Telegram уйдёт «НЕ ПОДТВЕРЖДАЮТСЯ», а не «НЕ УХОДЯТ» |
| `--max-per-hour 3` | лимит частоты | `ERROR модем упёрся в лимит частоты СМС`, тревоги о поломке нет |
| `expires_at` в прошлом | очередь после долгого обрыва | `WARNING мост отбросил протухшую команду`, тревоги нет |

Отказ и молчание — разные симптомы: первое значит «модем не смог», второе —
«шлюза нет на месте», и чинятся они по-разному. Поэтому в тексте они
называются по-разному.

Последнее различие принципиально: если считать поломкой любой отказ, то
после восстановления связи разгружающаяся очередь поднимет ложную тревогу
ровно тогда, когда всё только что починилось.

**Настоящие СМС.** Нужен шлюз, выполняющий
[контракт](docs/sms-gateway-contract.md). Готовый пример под USB-модем
openstick с `wms_sms_daemon` лежит в `extras/openstick/sms_mqtt_bridge.py`;
он настраивается переменными окружения (`MQTT_HOST`, `MQTT_USER`,
`MQTT_PASS`, `OPENSTICK_ID`, `SMS_TRUSTED_NUMBERS`, `SMS_MAX_PER_HOUR`) и
живёт на самом модеме. Под другой модем меняется одна функция — вызов
отправляющей утилиты. После установки поправьте `sms_topic` и `ack_topic`
под id вашего шлюза и выключите заглушку.

### 7. Разнесённая установка (необязательно)

Нужна ровно в одном случае: демон должен жить не там, где симка. У домашнего
канала бывает и авария, и отключение света, поэтому демон уезжает в облако, а
СМС уходят **обратным** каналом через дом.

```
  облако                         дом
  ┌──────────────┐   WireGuard   ┌──────────────┐      ┌────────┐
  │ flightwatch  │◄─────────────►│  mosquitto   │─────►│ модем  │──► СМС
  │ mosquitto ───┼── мост ───────┤  (брокер)    │ MQTT │ + мост │
  │ MariaDB      │               │Home Assistant│      └────────┘
  └──────────────┘               └──────────────┘
```

Три вещи, каждая получена набитой шишкой:

1. **`AllowedIPs` узкие с обеих сторон** — по одному `/32`. Облако достаёт
   ровно до одного адреса дома и ни до чего больше; форвардинг не включается.
2. **`cleansession false` у моста** — пока туннель лежит, команда на СМС
   копится в облачном брокере и уходит после восстановления. С `true` она
   просто пропадает.
3. **ACL на домашнем брокере** — учётка моста умеет ровно два топика:
   написать в отправку СМС и прочитать подтверждение. Всё остальное из
   облака в дом не попадает, даже если демон это опубликует.

Файлы-заготовки в `extras/split-deployment/`:

* `wg0-cloud.conf`, `wg0-home.conf` — туннель. Ключи генерируются `wg genkey`,
  в репозиторий не попадают.
* `mosquitto-bridge.conf` — мост, ставится на **облачный** брокер.
* `mosquitto-acl` — ACL домашнего брокера.

На облаке наружу должны смотреть ровно два порта — ssh и WireGuard:

```bash
sudo ufw allow 22/tcp && sudo ufw allow 51820/udp && sudo ufw enable
```

Ни 1883, ни 8787 наружу не открываются никогда: брокер слушает петлю, `fwapi`
дополнительно ограничен `IPAddressAllow=localhost` в юните.

Про ACL важное: как только в `mosquitto.conf` появляется `acl_file`,
запрещено всё, что не разрешено явно, — а `#` **не** покрывает `$SYS`. Если
не добавить `topic read $SYS/#` каждому существующему пользователю, у них
молча пропадут системные топики.

Второе: `mqtt_client_id` у двух экземпляров должен различаться. Одинаковый —
это дуэль сессий, брокер бесконечно выкидывает то одного, то другого.

## Контракт для агента (необязательно)

Если хочется управлять рейсами разговором, а не ssh, в комплекте есть узкий
контракт. Идея простая: у агента **нет** доступа к каталогу демона — границу
ставит ядро (`InaccessiblePaths` в юните агента), а не уговоры в промпте.
Всё общение идёт через `fwapi` на петле, и набор операций там фиксированный.

```
чтение     status, config, log, sources, sql, board, history
изменение  add-flight, remove-flight, set
```

`history` считает пунктуальность рейса **в службе, а не в модели**: делит
наблюдения по расписаниям (один номер может летать и утром, и днём),
отдаёт медиану рядом со средним, счёт задержек 30+ и 60+ минут, окно за
неделю отдельно от общего и помечает строки, где разница времён не сходится
с задержкой. Это не удобство, а граница ответственности: арифметику, в
которой модель ошибается предсказуемо, лучше не поручать модели.

Разделение по трём командам сделано осознанно:

* `fwctl` — только чтение, список операций **зашит в код клиента**, поэтому
  его можно разрешить агенту без подтверждения: он физически не умеет менять.
* `fwctl-write` — добавить/снять рейс. Тоже без подтверждения: это рутина.
* `fwctl-config` — правка настроек. Всегда спрашивает и намеренно **не**
  вносится в allowlist: `set --key notify --value false` молча выключил бы
  оповещения сразу по всем рейсам.

Установка:

```bash
sudo mkdir -p /opt/fwapi && sudo cp src/fwapi.py /opt/fwapi/
sudo cp cli/fwctl cli/fwctl-write cli/fwctl-config /usr/local/bin/
sudo chmod 755 /usr/local/bin/fwctl*
sudo groupadd -f fwapi

# токен, которым fwctl авторизуется в fwapi
openssl rand -hex 24 | sudo tee /etc/fwapi.token >/dev/null
sudo chown root:fwapi /etc/fwapi.token && sudo chmod 640 /etc/fwapi.token

# пароль ЧИТАЮЩЕГО пользователя базы из шага 1 — путь зашит в fwapi.py
printf '%s' 'ПАРОЛЬ2' | sudo tee /etc/fwapi.dbpass >/dev/null
sudo chown root:flightwatch /etc/fwapi.dbpass && sudo chmod 640 /etc/fwapi.dbpass

sudo cp systemd/fwapi.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now fwapi
```

Проверка, что контракт живой и что читающая учётка действительно только
читает:

```bash
sleep 3                            # службе нужен момент, чтобы занять порт
fwctl status                       # ожидается: ok true и список рейсов
fwctl sources --hours 1            # ходит в базу под fwread
fwctl sql "DELETE FROM flights"    # ожидается отказ: только SELECT и WITH
```

Пользователя агента добавьте в группу `fwapi` — только это и даёт ему доступ
к токену. Служба слушает `127.0.0.1:8787` и ограничена `IPAddressAllow=localhost`:
наружу и в туннель она не торчит.

`agent/SKILL.md` — скил для [OpenClaw](https://github.com/openclaw/openclaw):
что агенту можно, чего нельзя и как отвечать про рейсы. Под другой агентский
рантайм переписывается тривиально — это обычный markdown с описанием команд.

## Почему CLI, а не MCP

Сравнивали. MCP-сервер держит описания всех инструментов в контексте каждого
запроса; CLI со скилом подгружает описание только тогда, когда оно
понадобилось, — на девяти операциях это заметная разница в постоянных
накладных токенах, а поведенческой разницы не видно: агент одинаково хорошо
вызывает и то и другое.

Второй довод важнее первого: allowlist на бинарник — это граница, которую
видно в системе (`systemd`, права, группы), а не в конфиге агентского
рантайма. Её можно проверить чужими руками и она не исчезает при обновлении
агента.

## Чего здесь нет

* **Ключей и паролей.** Ни одного. Всё читается из файлов, пути — в конфиге.
* **Гарантий по источникам.** Шлюз TAV и JSON Звартноца недокументированные;
  они могут измениться или закрыться в любой день. Именно поэтому у каждого
  аэропорта есть запасной источник и молчаливый откат.
* **Данных в схеме.** `docs/schema.sql` — структура, `--no-data`.

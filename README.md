# flightwatch

Демон слежения за конкретными рейсами. Опрашивает табло аэропортов и FR24,
замечает изменения раньше, чем о них объявят, и пишет человеку в Telegram и
СМС. СМС уходят через собственный модем — то есть доходят и тогда, когда
интернета у адресата нет.

Задача не «показать статус рейса», а **разбудить решением**: пора выезжать,
стыковка под угрозой, борт под ваш рейс ещё не вылетел, аэропорт сыплется.
Всё, что не требует действия, система молчит.

## Что она умеет

* **Несколько источников на аэропорт.** Публичный шлюз TAV, открытый JSON
  Звартноца, табло Черногории, XML Белграда, FR24 как общий запасной. У
  каждого источника свой горизонт и свои поля; при осечке молча откат на
  следующий, с экспоненциальным отстоем.
* **Ротация борта.** Самый ранний сигнал: борт, который ещё не вылетел в
  вашу сторону, делает вылет по расписанию невозможным за много часов до
  того, как табло признает задержку.
* **Стыковка.** Считается не «рейс опоздал на N», а «до закрытия выхода на
  следующий рейс осталось M минут» — решение принимается по второму.
* **Сбой аэропорта.** Оценивается по всей доске в операционном окне, а не по
  вашим пяти рейсам. Пороги входа и выхода разные — иначе на границе
  начинается дребезг и сообщения каждые полчаса.
* **Прогноз опоздания** с записью горизонта в базу, чтобы веса можно было
  калибровать по факту, а не на глаз.
* **Плановые сводки.** Молчание недоказательно: в заданное время приходит
  сводка, даже когда всё спокойно, — иначе человек не знает, жива ли система.
* **Сенсоры Home Assistant** через MQTT discovery (по желанию).
* **Контракт для LLM-агента** — узкий набор операций, см. ниже.

## Из чего состоит

```
src/flightwatch.py       демон
src/fwapi.py             узкий HTTP-контракт на 127.0.0.1:8787 (для агента)
cli/fwctl                чтение состояния  (безопасно, можно без подтверждения)
cli/fwctl-write          добавить / снять рейс
cli/fwctl-config         правка настроек демона (намеренно отдельно)
modem/sms_mqtt_bridge.py мост SMS <-> MQTT, живёт НА модеме
systemd/*.service        юниты с песочницей
docs/schema.sql          схема базы (структура, без данных)
examples/                WireGuard, мост mosquitto, ACL брокера
agent/SKILL.md           скил для агента OpenClaw
config.example.json      шаблон конфига
```

## Топология

Минимальная установка — одна машина: демон, MariaDB, mosquitto, модем в той
же сети. Всё остальное необязательно.

Разнесённый вариант, ради которого писалась половина кода: демон живёт на
облачном сервере (у домашнего канала бывает и авария, и отключение света), а
СМС отправляет **обратным** каналом через дом — там стоит модем с SIM-картой.

```
  облако                         дом
  ┌──────────────┐   WireGuard   ┌──────────────┐      ┌────────┐
  │ flightwatch  │◄─────────────►│  mosquitto   │─────►│ модем  │──► СМС
  │ mosquitto ───┼── мост ───────┤  (брокер)    │ MQTT │ + мост │
  │ MariaDB      │               │ Home Assistant│      └────────┘
  └──────────────┘               └──────────────┘
```

Здесь важны три вещи, и каждая была получена набитой шишкой:

1. **`AllowedIPs` узкие с обеих сторон** — по одному `/32`. Облако достаёт
   ровно до одного адреса дома и ни до чего больше; форвардинг не включается.
2. **`cleansession false` у моста** — пока туннель лежит, команда на СМС
   копится в облачном брокере и уходит после восстановления. С `true` она
   просто пропадает.
3. **ACL на домашнем брокере** — учётка моста умеет ровно два топика:
   написать в отправку СМС и прочитать подтверждение. Всё остальное из
   облака в дом не попадает, даже если демон это опубликует.

## Установка

### 1. База

```bash
sudo mysql -e "CREATE DATABASE flightwatch CHARACTER SET utf8mb4;"
sudo mysql -e "CREATE USER 'flightwatch'@'127.0.0.1' IDENTIFIED BY 'ПАРОЛЬ';"
sudo mysql -e "GRANT ALL ON flightwatch.* TO 'flightwatch'@'127.0.0.1';"
sudo mysql flightwatch < docs/schema.sql
```

Справочные таблицы (`airline_rules`, `airport_rules`, `travel_profiles`,
`connect_defaults`) приезжают пустыми — демон работает и без них, они только
уточняют оценки.

Если планируете `fwapi`, заведите ещё и **читающего** пользователя: `fwctl
sql` ходит именно им, поэтому «только SELECT» держится не регуляркой, а
правами базы.

```bash
sudo mysql -e "CREATE USER 'fwread'@'127.0.0.1' IDENTIFIED BY 'ПАРОЛЬ2';"
sudo mysql -e "GRANT SELECT ON flightwatch.* TO 'fwread'@'127.0.0.1';"
```

### 2. Каталог и права

Демон не должен уметь переписывать собственный код — отсюда разделение
владельцев и отдельный подкаталог `run/` под всё изменяемое.

```bash
sudo useradd -r -s /usr/sbin/nologin flightwatch
sudo mkdir -p /opt/flightwatch/run
sudo cp src/flightwatch.py /opt/flightwatch/
sudo chown -R root:root /opt/flightwatch
sudo chown flightwatch:flightwatch /opt/flightwatch/run
```

Конфиг лежит в `run/`, а в каталоге кода на него симлинк. Так и каталог кода
остаётся закрытым на запись, и атомарная подмена файла работает: `os.replace`
требует права на **каталог**, а не на файл.

```bash
sudo cp config.example.json /opt/flightwatch/run/config.json
sudo ln -s run/config.json /opt/flightwatch/config.json
sudo chown flightwatch:flightwatch /opt/flightwatch/run/config.json
sudo chmod 640 /opt/flightwatch/run/config.json
```

### 3. Секреты — файлами, не в конфиге

```bash
printf '%s' 'ПАРОЛЬ'        | sudo tee /opt/flightwatch/.mysql_pass >/dev/null
printf '%s' 'ПАРОЛЬ_MQTT'   | sudo tee /opt/flightwatch/.mqtt_pass  >/dev/null
printf '%s' 'ТОКЕН_БОТА'    | sudo tee /opt/flightwatch/.tg_token   >/dev/null
sudo chmod 640 /opt/flightwatch/.*_pass /opt/flightwatch/.tg_token
sudo chown root:flightwatch /opt/flightwatch/.*_pass /opt/flightwatch/.tg_token
```

В конфиге хранятся только **пути** к этим файлам. В репозитории их нет и быть
не должно — см. `.gitignore`.

### 4. Окружение и запуск

```bash
sudo python3 -m venv /opt/flightwatch/venv
sudo /opt/flightwatch/venv/bin/pip install -r requirements.txt
sudo cp systemd/flightwatch.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now flightwatch
```

Проверка, что он действительно поднялся, а не просто «active»:

```bash
journalctl -u flightwatch -n 40 --no-pager | grep -E "MQTT|рейс"
```

В логе должна быть строка `MQTT: подключён`. Это не украшение: paho отдаёт
ошибку аутентификации асинхронно, `connect()` при неверном пароле не падает —
юнит будет `active` с мёртвым брокером, пока не посмотришь в лог.

### 5. Конфиг

Скопируйте `config.example.json` и правьте. Ключи, которые нужны сразу:

| ключ | что это |
|---|---|
| `flights` | список отслеживаемых рейсов (см. ниже) |
| `channels` | `["telegram", "sms"]` — порядок и есть приоритет |
| `telegram_chat_id`, `telegram_token_file` | куда и чем писать |
| `sms_to`, `sms_topic`, `ack_topic` | номер и топики моста СМС |
| `mqtt_*` | брокер; `mqtt_client_id` уникален **на каждый экземпляр** |
| `discovery_prefix` | префикс MQTT discovery для Home Assistant |
| `notify` | глобальный выключатель отправки |
| `briefings` | плановые сводки: время местное для указанного аэропорта |

Рейс:

```json
{
  "flight": "XX1234", "date": "2026-01-01", "airport": "AAA",
  "direction": "departure", "to": "BBB",
  "title": "Город А - Город Б",
  "owner": "self",
  "mct_min": 60, "gate_close_min": 20,
  "extra_sms_to": []
}
```

`owner: "other"` — чужой рейс, за которым следят ради встречи. Влияет на
формулировки: будить владельца телефона «пора выезжать» по чужому рейсу
нельзя.

Демон перечитывает конфиг сам по `mtime`, цикл — `poll_seconds` (90 с по
умолчанию). Перезапуск после правки не нужен.

### 6. Мост СМС (если нужны СМС)

`modem/sms_mqtt_bridge.py` кладётся **на модем** и настраивается переменными
окружения: `MQTT_HOST`, `MQTT_USER`, `MQTT_PASS`, `OPENSTICK_ID`,
`SMS_TRUSTED_NUMBERS`, `SMS_MAX_PER_HOUR`. Он подписан на
`openstick/<id>/sms/send` и отвечает в `openstick/<id>/sms/sent`.

Написан под openstick-модем с `wms_sms_daemon`; под другой модем меняется
одна функция — вызов отправляющей утилиты.

Две вещи, без которых он ведёт себя неприятно:

* `clean_session=False` — модем перезагружается, и без этого команды,
  пришедшие в момент перезагрузки, теряются молча.
* У команды есть `expires_at`. Просроченную мост **выбрасывает**, и это не
  отказ канала: «рейс задержан» получасовой давности будить человека уже не
  должно. Отличать просрочку от поломки канала обязательно, иначе система
  сама себе шлёт «СМС НЕ УХОДЯТ».

### 7. Разнесённая установка

Файлы-заготовки в `examples/`:

* `wg0-cloud.conf`, `wg0-home.conf` — туннель. Ключи генерируются `wg genkey`,
  в репозиторий не попадают.
* `mosquitto-bridge.conf` — мост, ставится на **облачный** брокер.
* `mosquitto-acl` — ACL домашнего брокера.

Про ACL важное: как только в `mosquitto.conf` появляется `acl_file`,
запрещено всё, что не разрешено явно, — а `#` **не** покрывает `$SYS`. Если
не добавить `topic read $SYS/#` каждому существующему пользователю, у них
молча пропадут системные топики.

Второе: `mqtt_client_id` у двух экземпляров должен различаться. Одинаковый —
это дуэль сессий, брокер бесконечно выкидывает то одного, то другого.

## Контракт для агента (необязательно)

Если хочется управлять рейсами разговором, а не ssh, в комплекте есть узкий
контракт. Идея простая: у агента **нет** доступа к каталогу демона — границу
ставит ядро (`InaccessiblePaths` в юните агента), а не уговоры в промпте.
Всё общение идёт через `fwapi` на петле, и набор операций там фиксированный.

```
чтение     status, config, log, sources, sql, board
изменение  add-flight, remove-flight, set
```

Разделение по трём командам сделано осознанно:

* `fwctl` — только чтение, список операций **зашит в код клиента**, поэтому
  его можно разрешить агенту без подтверждения: он физически не умеет менять.
* `fwctl-write` — добавить/снять рейс. Тоже без подтверждения: это рутина.
* `fwctl-config` — правка настроек. Всегда спрашивает и намеренно **не**
  вносится в allowlist: `set --key notify --value false` молча выключил бы
  оповещения сразу по всем рейсам.

Установка:

```bash
sudo mkdir -p /opt/fwapi && sudo cp src/fwapi.py /opt/fwapi/
sudo cp cli/fwctl cli/fwctl-write cli/fwctl-config /usr/local/bin/
sudo chmod 755 /usr/local/bin/fwctl*
openssl rand -hex 24 | sudo tee /etc/fwapi.token >/dev/null
sudo groupadd -f fwapi
sudo chown root:fwapi /etc/fwapi.token && sudo chmod 640 /etc/fwapi.token
sudo cp systemd/fwapi.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now fwapi
```

Пользователя агента добавьте в группу `fwapi` — только это и даёт ему доступ
к токену. Служба слушает `127.0.0.1:8787` и ограничена `IPAddressAllow=localhost`:
наружу и в туннель она не торчит.

`agent/SKILL.md` — скил для [OpenClaw](https://github.com/openclaw/openclaw):
что агенту можно, чего нельзя и как отвечать про рейсы. Под другой агентский
рантайм переписывается тривиально — это обычный markdown с описанием команд.

## Почему CLI, а не MCP

Сравнивали. MCP-сервер держит описания всех инструментов в контексте каждого
запроса; CLI со скилом подгружает описание только тогда, когда оно
понадобилось, — на девяти операциях это заметная разница в постоянных
накладных токенах, а поведенческой разницы не видно: агент одинаково хорошо
вызывает и то и другое.

Второй довод важнее первого: allowlist на бинарник — это граница, которую
видно в системе (`systemd`, права, группы), а не в конфиге агентского
рантайма. Её можно проверить чужими руками и она не исчезает при обновлении
агента.

## Чего здесь нет

* **Ключей и паролей.** Ни одного. Всё читается из файлов, пути — в конфиге.
* **Гарантий по источникам.** Шлюз TAV и JSON Звартноца недокументированные;
  они могут измениться или закрыться в любой день. Именно поэтому у каждого
  аэропорта есть запасной источник и молчаливый откат.
* **Данных в схеме.** `docs/schema.sql` — структура, `--no-data`.
